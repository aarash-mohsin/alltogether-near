# AllTogether NEAR contract and integration

This folder contains a real Rust NEAR escrow and a separate NEP-141/NEP-145 test token. Local SQLite transactions in the app are not NEAR transactions. The scripts below support testnet only and reject mainnet. Deployment and live-flow evidence, when generated by the coordinator, is separate from this source/build documentation.

## Contract artifacts

- Escrow: `contract/target/near/alltogether_escrow.wasm`.
- Test token: `contract/target/near/alltogether_test_usd/alltogether_test_usd.wasm`.
- SDK: exact `near-sdk = 5.30.0`, `near-contract-standards = 5.30.0`; dependencies locked in `contract/Cargo.lock`.
- Compiler used during development: Rust 1.99.1 GNU, `wasm32-unknown-unknown`, cargo-near 0.22.0.

Both artifacts have been successfully compiled and processed by cargo-near's wasm-opt step. This is a host build, not a claim of byte-identical container reproducibility or a third-party audit. Native test results and live testnet receipts are recorded separately in the project's evidence document.

## Initializers

Escrow `new` arguments:

```json
{"config":{"dao_id":"YOUR-VERIFIED-DAO.testnet","token_id":"YOUR-TOKEN.testnet","token_decimals":6,"token_symbol":"testUSD"}}
```

Token `new` arguments:

```json
{"owner_id":"YOUR-DEDICATED-SUPPLY-ACCOUNT.testnet","total_supply":"1000000000000"}
```

The token has fixed initial supply, six decimal places, and metadata explicitly stating it has no monetary value. It is not USDC. There is no privileged minting method or escrow balance sweep.

## Escrow methods

| Method | Arguments | Authorization / behavior |
| --- | --- | --- |
| `get_config` | `{}` | Fixed DAO/token, limits and version |
| `quote_campaign_storage` | `{"leg_count":3}` | Returns the measured-serialization storage bound and required native deposit |
| `create_campaign` | `{"input":{"title":"...","summary":"...","detail":"...","deadline_ms":"...","legs":[{"title":"...","purpose":"...","beneficiary":"...","budget":"600000000","declared_sponsor_cap":"200000000"}]}}` | Caller is organizer; attach at least the storage quote |
| `get_campaign` | `{"campaign_id":"1"}` | Campaign, immutable terms/hash, exact funding and accounting |
| `list_campaigns` | `{"from_index":"0","limit":20}` | Bounded page, at most 50 |
| `ft_on_transfer` | Standard token callback | Only the configured FT may invoke; token-authenticated `sender_id` is authoritative |
| `remove_pledge` | `{"campaign_id":"1","leg_id":0,"amount":"1000000"}` | Current caller's active contribution, strictly before close; converts to separate credit |
| `finalize` | `{"campaign_id":"1"}` | Anyone at/after close; all-or-none entitlement allocation; bounded by three budgets |
| `materialize_refund` | `{"campaign_id":"1"}` | Failed campaign; caller consumes at most three positions once |
| `get_account_campaign` | `{"campaign_id":"1","account_id":"..."}` | Positions and fixed-recipient credits |
| `get_credit` / `get_attempt` | `{"credit_key":"1:withdrawal:alice.testnet:-"}` | Credit and bounded latest attempt |
| `claim_credit` | Same credit key | Attach exactly 1 yoctoNEAR, at least 60 Tgas; contributor credit requires its owner; beneficiary/DAO credits can be triggered by anyone |
| `on_transfer_result` | `{"credit_key":"...","nonce":"1"}` | Private callback only; reads actual promise result, never a user-supplied success flag |
| `get_accounting` | `{"campaign_id":"1"}` or `{"campaign_id":null}` | Campaign or global exact book categories |

Outer campaign/accounting/credit views use Rust snake_case. Immutable `terms` and its legs use camelCase to match the shared canonical fixture. Amounts and IDs are decimal strings; leg indices are small integers.

Standard token transfer messages:

```json
{"v":1,"action":"sponsor","campaign_id":"1","terms_hash":"EXACT-HASH"}
{"v":1,"action":"pledge","campaign_id":"1","leg_id":0,"terms_hash":"EXACT-HASH"}
```

Messages are strict, bounded to 2 KiB, and must contain exactly the expected fields. Sponsor receipt must come from the fixed DAO, be the exact complete reserve, and arrive before closing. A rejected logical deposit returns the full unused amount through NEP-141; callers must inspect the FT resolver outcome and balances, not infer acceptance from a top-level transaction hash.

## Governance and custody

Sputnik is the existing governance system. The exact proposal is a `FunctionCall` to the configured FT's `ft_transfer_call`, with the escrow as receiver and the sponsor message above. The script reads `get_policy` and uses its actual proposal bond. It does not implement another council, fabricate votes, or equate approval with accepted reserve funding.

After execution, the campaign escrow holds the expressly approved sponsor tranche and pledges. The remainder of the DAO treasury stays in Sputnik. A separate native balance pays storage; it is not testUSD principal.

## Script configuration

```powershell
$env:NEAR_NETWORK = 'testnet'
$env:NEAR_RPC_URL = 'https://test.rpc.fastnear.com'
$env:NEAR_DAO_ID = 'YOUR-VERIFIED-DAO.testnet'
$env:NEAR_TOKEN_ID = 'YOUR-VERIFIED-TOKEN.testnet'
$env:NEAR_ESCROW_ID = 'YOUR-VERIFIED-ESCROW.testnet'
node scripts/near/preflight.mjs
node scripts/near/proposal.mjs 1
node scripts/near/verify.mjs 1
```

These commands perform genuine RPC reads, export a prepared proposal, and reconcile observed state. Proposal export is explicitly **not submission**. Read-only preflight records metadata, token registration bounds, DAO policy/version, escrow configuration and code hash.

`deploy.mjs escrow|token` requires an already-created dedicated target account and an ignored `.secrets` credential file selected by `NEAR_DEPLOY_KEY_FILE`. It refuses to read user wallet stores. `NEAR_TOKEN_OWNER_ID` is required for token initialization. Existing deployed code is not overwritten unless `ALLOW_TESTNET_REDEPLOY=yes`; an already initialized state is never silently reset. Full-access deployment keys, if retained for testnet development, remain an upgrade trust root and must be disclosed.

No script prints private keys. Public evidence JSON contains only configuration, artifact hashes, receipts and read results. Dedicated generated testnet accounts are fixtures, not the user's wallet.

## Settlement and failure semantics

Each campaign has independent active principal, sponsor reserve, failed principal, available credits, pending transfers and cumulative paid categories. At success all fixed beneficiary credits are created in one state transition. Token transfers happen separately and asynchronously; one failed beneficiary payout cannot revoke another beneficiary's credit.

A withdrawal removes active funding immediately. Its failed token transfer restores the withdrawal credit, never the pledge. A callback nonce prevents stale/duplicate outcomes from paying or restoring twice. Return data is bounded; an oversized successful FT result still counts as successful payment, avoiding accidental double credit.

If an onchain attempt remains pending, inspect transaction/receipt outcomes and contract state. Do not reset it merely because a UI timed out: the token may already have moved. There is no admin pending-reset or balance-sweep method. The prototype deliberately exposes this operational limitation rather than adding an unsafe recovery override.

## Scope of verification

Native VM-context tests exercise contract logic; they are not proof of a full cross-contract token resolver path. Compiled WASM is not a deployment. Actual testnet execution must record the real DAO/token/escrow identities, code hash, downstream receiver/resolver/callback receipts, and before/after token balances. The coordinator's integration evidence identifies which of these stages actually ran.
